<objective>
Build the three magic-link RPCs in the `staff_app` schema (inside HITO's project) — `staff_app.get_public_offer`, `staff_app.accept_offer`, `staff_app.decline_offer` — as SECURITY DEFINER functions that are the ONLY door anon has to the offers/crew data, and prove them correct entirely in SQL. Clone HITO's proven `00008_proposal_acceptance.sql` shape but close its two documented gaps: use a 256-bit token hashed at rest (HITO stores a 96-bit raw token), and enforce `expires_at` inside the RPC (HITO omits the expiry check). All objects live under `staff_app`; HITO's public.* tables are never touched (D-03).

Purpose: DATA-04 — the login-less offer lifecycle is the app's core security boundary. It must be single-use, idempotent, expiry-enforcing, leak-free, and advisor-clean, verified in SQL before any UI (Phase 4) consumes it.
Output: migration `staff_app_0003_magic_link_rpcs` + a recorded SQL test-harness run proving all seven cases.

Slice (data-layer, SQL-provable): after this plan, calling the RPCs against a real seeded token in SQL demonstrates the full offer accept/decline lifecycle without a line of app code.

**Phase 4 note (do NOT implement now):** because these RPCs live in the `staff_app` schema (not `public`), PostgREST/REST access from the app will need either exposing `staff_app` in the project's exposed-schemas config OR thin `public` wrapper functions that call the staff_app RPCs. This is a Phase 4 concern only — record it, do not build it here. (Contrast with 01-03's intake function, which is deliberately placed in `public` so the live web form can call it without any config change.)
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anon → staff_app.offers/crew | anon reaches offer data ONLY through the three granted SECURITY DEFINER RPCs in staff_app, scoped by a per-request token |
| emailed URL → DB | The raw token travels in the URL; the DB stores only its hash |
| staff_app RPCs → HITO public.* | The RPCs operate only on staff_app tables; HITO's public schema is never referenced (D-03) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-04 | Spoofing / Elevation | magic-link token | mitigate | 256-bit `extensions.gen_random_bytes(32)`; stored only as sha256 `token_hash`; raw token never persisted — brute-force and DB-leak-replay both defeated |
| T-01-05 | Tampering / Elevation | RPC search_path | mitigate | `SET search_path = staff_app, pg_temp` + schema-qualified `extensions.*`; get_advisors zero NEW function_search_path_mutable (blocker) |
| T-01-06 | Information Disclosure | get_public_offer payload | mitigate | Returns first-name + offer/gig/org only; no cv_url/email/telefono/documento/other applicants — asserted in Task 2 case 3 |
| T-01-07 | Tampering | replay / double-accept | mitigate | Guard `status IN ('sent','viewed')` + `expires_at > now()`; crew INSERT `ON CONFLICT DO NOTHING` → second click is a no-op |
| T-01-08 | Tampering | preview-bot GET auto-accept | accept (this phase) | accept/decline are POST-invoked RPCs; the no-state-change-on-GET boundary is enforced by the UI in Phase 4 — documented in the RPC comment now |
| T-01-SC | Tampering | package installs | accept | No package installs — pure SQL via MCP |
</threat_model>
